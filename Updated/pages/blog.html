Development notes

Developing the browser version

The first version of Airgead was a C++ console program. It collects investment inputs and reports annual growth with and without monthly deposits.

For the website, I focused on making those results easier to explore. Editable fields, immediate calculations, and side-by-side comparisons allow users to test assumptions without repeating the console workflow.

I kept the C++ implementation in the repository as a separate program. The website is a companion implementation, not a replacement for the original code.

I built the site with HTML, CSS, and native JavaScript modules. Shared investment fields support the calculator and comparison pages, while separate modules handle calculation, storage, and export.

Separating the calculation from the interface made both easier to maintain. A page can change how it presents results without changing the underlying compounding rules.

The order of operations matters: the monthly contribution is added before interest. Moving it after the interest step would produce different balances, even when the inputs are identical.

I used tests to protect that behavior and other boundary cases. Visual presentation is important, but it cannot compensate for incorrect financial figures.

Results and interface

Presenting financial results clearly

A projected final balance combines the money contributed and the interest calculated. Showing only the total makes it difficult to tell which part caused the increase.

I therefore display principal and interest separately. Principal includes the starting balance and monthly deposits; interest is the amount added by the model.

Charts help readers compare growth over time. Tables provide the annual figures needed to inspect individual years and check the difference between scenarios.

I included descriptive context for charts, row headers for tables, and keyboard-accessible scrolling for wide data. These choices make the numbers useful beyond a single visual format.

Keeping multiple presentations of the same results adds complexity. I reduced the risk of inconsistency by deriving summaries, charts, and tables from the same calculation output.

Input errors need clear handling. The calculator rejects malformed values and results beyond its supported numeric range instead of displaying misleading totals.

Charts also have limits on smaller screens. I kept the numerical tables and text explanations available rather than relying on chart labels or color alone.

Storage and data handling

Implementing browser-local saved plans

Saving a plan introduces a different problem from calculating it. Browser storage can contain incomplete, outdated, or modified data, so records need validation when they are read.

The Results page can retrieve the current calculation after navigation. Named saved plans store the inputs and calculated data needed to reopen a previous scenario.

Saved Plans supports reopening and deleting records, including a deletion confirmation. CSV export is handled separately and produces a downloadable file from the annual results.

This storage is local to the browser. It is not an account database, it does not synchronize devices, and clearing site data can remove saved plans. Demo sign-in is not authentication.

I tested normal storage operations and failure cases, including invalid records, repeated saves, exports, and deletion. These cases matter because a feature must remain predictable when data is not ideal.

The calculation, storage, and export modules have distinct responsibilities. That makes it easier to understand where validation belongs and what a change might affect.

The main lesson from this implementation is to describe the system accurately. Browser-local saving is useful for a static demonstration, but it should never be presented as secure online account storage.
