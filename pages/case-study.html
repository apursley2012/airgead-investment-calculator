Project goals

I built Airgead to make the relationship between contributions, interest, and time easier to understand. A single final balance can hide how much money was deposited and how much growth the calculation produced.

The project started as a C++ console application that reports investment growth with and without monthly deposits. I retained that implementation and developed a separate browser version to make the same calculations easier to explore.

The website is an educational calculator, not a financial service. My development goals were to preserve the underlying rules, organize the code clearly, and present the results in a usable interface.

Project scope

The repository contains two implementations. Original/ holds the C++17 console program and its tests. Updated/ holds the static website, its browser modules, assets, and tests.

The website includes a calculator, annual results, a two-scenario comparison, browser-local saved plans, CSV export, educational material, and a demo sign-in. Each feature supports a specific part of the calculation and review process.

Code organization

I separated the calculation from page rendering. The browser calculator module handles growth projections, while the storage and export modules handle saved records and CSV output. This allows each responsibility to be tested independently.

Page-specific JavaScript connects the shared modules to the calculator, comparison, results, saved-plan, and sign-in pages. Shared components handle navigation and repeated form patterns so the pages behave consistently.

The HTML provides the content and page structure. Shared CSS covers common elements, while page stylesheets handle layouts specific to individual screens. This division makes targeted changes easier to review.

Calculation rules

Both projections use a fixed annual percentage rate converted into a monthly rate. One projection grows the initial balance alone; the other adds a contribution every month.

The deposit scenario calculates each month as (current balance + monthly deposit) × (1 + monthly rate). The no-deposit scenario applies the monthly rate to the current balance without adding funds. Annual results are derived from these monthly steps.

I kept the deposit-before-interest order used by the original implementation. Changing that order would change the results, so I treated it as a calculation requirement rather than a presentation detail.

The browser checks inputs and rejects results outside its supported numeric range. Its timeframe is limited to 80 whole years. The C++ program remains a separate implementation rather than being silently replaced by the website.

Interface design

I used a restrained green-and-neutral palette, clear typography, and consistent layouts. The purpose of the visual design is to make the inputs and results readable without competing with the financial information.

The calculator groups related inputs. Results separate principal from interest, and Compare shows the makeup of each scenario’s final balance. These details help explain why two totals differ.

The layout adapts to smaller screens, including scrollable annual tables and mobile navigation. Charts provide a quick overview, while tables preserve access to individual values.

Browser storage and saved plans

All calculations run in the browser. The current result is saved locally so it can be displayed after navigation, and named plans can be retained for later use in the same browser.

I validate records read from storage rather than assuming they are correct. The storage module checks the input structure and recalculates expected results before using saved data.

Users can save, reopen, and delete plans. CSV export creates a file locally, and the saved-plan view can respond to storage changes from another tab. The demo sign-in does not provide real authentication.

Browser storage keeps the website suitable for static hosting, but it has limits: no cross-device sync, no server backups, and no secure user accounts. A production account system would require a different architecture.

Accessibility and usability

I included labeled fields, semantic headings, visible focus indicators, a skip link, and text or table alternatives to chart-only information. These features help people use the interface with different devices and input methods.

The mobile navigation supports keyboard interaction, including Escape to close the menu and focus returning to the trigger. Reduced-motion preferences are also considered for animated output.

These features are useful accessibility measures, but they do not establish formal compliance. A complete screen-reader and real-device audit remains necessary.

Testing and validation

I added C++ regression tests and Node.js tests covering growth calculations, input validation, stored-plan integrity, CSV formatting, and page resources.

I also compared calculation behavior across the C++ and JavaScript versions and exercised selected browser workflows. These checks reduce regression risk but cannot guarantee that every visual or interaction issue has been found.

Local testing is not a substitute for checking a published site. Deployment, browser differences, and assistive-technology behavior require their own verification.

Technical decisions and limitations

I chose native JavaScript modules because the project is small enough to remain understandable without a framework or build pipeline. The trade-off is that I manage component behavior and integration directly.

I used browser storage to demonstrate plan persistence on a static site. It supports reopening plans on the same device but is not suitable for secure accounts or reliable synchronization.

I used a constant-rate model because it matches the original calculation and makes the results reproducible. It is not a simulation of real market returns, fees, taxes, or inflation.

I presented charts and tables together because they answer different questions: charts reveal trends, while tables provide figures that can be inspected year by year.

This project demonstrates how I approach an existing codebase: preserve its required behavior, separate responsibilities, validate data, test the important calculations, and communicate limitations clearly.
